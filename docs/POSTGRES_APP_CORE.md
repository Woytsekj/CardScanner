# PostgreSQL Application Core (Migration 0004)

Migration: `db/migrations/0004_app_core.sql`

This migration adds the first application-owned relational tables. It is
schema-only: it does not connect to, read, copy, or modify production SQLite.
The migration runner applies it only to the PostgreSQL database selected by
`CARD_SCANNER_POSTGRES_DSN`.

## Tables

All tables in this migration live in the `app` schema:

| Table | Purpose |
| --- | --- |
| `people` | Named collection owners, with active state |
| `users` | Web login accounts, password hashes, roles, and optional default person |
| `login_attempts` | Login rate-limit state |
| `app_state` | String-valued application key/value state |
| `app_migrations` | One-time application data-migration markers |
| `inventory` | Physical owned copies and their owner, storage, deck, and vending allocation |
| `scan_log` | Scanner retry/idempotency records |
| `decklists` | Game-scoped deck records |
| `deck_cards` | Game-scoped deck requirements |

Catalog identities stay in `catalog`. Inventory, deck requirements, and deck
covers can hold optional canonical card/printing references while retaining
legacy Scryfall IDs, TCGplayer IDs, set codes, collector numbers, names, owner
labels, and cover IDs. A missing catalog resolution is not a reason to reject
or drop an otherwise valid legacy row.

## Important compatibility rules

- Internal integer IDs use `GENERATED BY DEFAULT AS IDENTITY` so an audited
  importer can preserve SQLite IDs.
- People and usernames have normalized case-insensitive unique indexes to
  reproduce SQLite `NOCASE` uniqueness.
- One non-null `users.person_id` can be linked to only one account. Unlinked
  service/vendor users remain valid.
- `inventory.owner` and `decklists.person_name` remain as display/source
  snapshots beside nullable `person_id` references. Deleting a person clears
  the relationship but does not erase the historical label.
- Inventory storage location is independent of deck allocation. Deleting a
  deck cascades its requirements and sets allocated inventory rows'
  `deck_id` to NULL; it does not delete the physical cards or alter location.
- Scan-log `row_id` deliberately has no foreign key. The row is an idempotency
  tombstone: a repeated `scan_id` must not add a card again just because the
  original inventory row was later removed.
- Composite game-scoped foreign keys prevent an MTG inventory/deck reference
  from being attached to a Pokémon, One Piece, or Riftbound catalog identity.
- Legacy `inventory.price` remains text. Later migrations add
  `catalog.product_price_history` for normalized price history and
  `catalog.provider_price_observations` for exact provider subtypes; neither
  changes the legacy inventory price field or imports production price data.

## Later schema additions (migrations 0005–0007)

Migration 0004 itself does not create the following legacy SQLite tables.
Their PostgreSQL schema equivalents were added by subsequent migrations:

| Legacy SQLite table | PostgreSQL table | Migration |
| --- | --- | --- |
| `card_metadata` | `catalog.provider_printing_metadata` | 0005 |
| `card_aliases` | `app.card_aliases` | 0005 |
| `card_price_mapping` | `catalog.printing_product_mappings` | 0005 |
| `card_rulings_cache` | `catalog.printing_rulings_cache` | 0005 |
| `price_history` | `catalog.product_price_history` | 0006 |
| `price_alert_log` | `app.price_alert_log` | 0006 |

These tables preserve provider-scoped identifiers and legacy source values.
Unresolved printing/product relationships can remain unresolved rather than
being fabricated during import.

Migration 0007 adds generic TCGCSV provider catalog structures:

- `catalog.provider_product_groups` stores provider groups with game,
  provider, and configured category scope.
- `catalog.provider_products` stores provider product metadata and retains
  game-specific `extended_data` without imposing a shared card schema.
- `catalog.provider_price_observations` stores exact provider subtype names
  and all five TCGCSV price fields independently.

The 0005–0007 migrations are schema-only. Their application to development
PostgreSQL did not import production SQLite rows or replace the production
databases. The separate artwork database tables remain represented in the
`catalog` migrations 0002 and 0003.

## Import prerequisites

Before any production import is designed or run:

1. Inspect the live SQLite `PRAGMA table_info` and index definitions for all
   source tables; this migration follows the current repository schema, but
   production schema drift must be checked.
2. Audit all source timestamp values and JSON text columns before converting
   them to PostgreSQL `TIMESTAMPTZ` and `JSONB`. Invalid values must be
   reported and resolved explicitly, never silently replaced or omitted.
3. Resolve owner/person and provider/catalog relationships in a staging pass.
   Preserve unresolved names and external IDs in the destination columns.
4. Preserve source primary keys and verify row counts, null counts, key
   coverage, relationship coverage, and representative values after import.
5. Run the importer against a disposable copy first. Production SQLite remains
   authoritative until a separate cutover plan is tested and explicitly
   approved.

No production import or application cutover is part of migration 0004.
